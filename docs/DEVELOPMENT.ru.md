# Cube Solver Lab (CubeLab) · Заметки для разработчиков

> Подробные заметки для разработчиков. Основной считается английская версия ([DEVELOPMENT.md](DEVELOPMENT.md)); этот перевод следует ей. Обзор проекта, запуск, тесты, развёртывание, лицензия и конфиденциальность — в [README](../README.ru.md).
> Упомянутые ниже `ref/` (кадры эталонного видео) и `screenshots/` (снимки экрана, создаваемые тестами) не входят в репозиторий; тесты создают папки для снимков при запуске.

Решатель головоломок, работающий целиком во фронтенде (статические HTML/CSS/JS, без бэкенда). Его отличительная черта — **вид графа**: рядом с 3D-головоломкой показан «граф перестановок», где каждая наклейка — узел. Для 3×3 это **три группы концентрических окружностей** (каждая группа из 3 окружностей = 3 слоя одной оси; центры образуют равносторонний треугольник, что даёт лепестковый узор с симметрией третьего порядка), а 54 узла стоят на пересечениях. При каждом повороте окружности этого слоя темнеют, 12 боковых наклеек движутся по дугам (с затухающими следами цвета наклейки), а 9 наклеек повёрнутой грани вращаются внутри своего кластера — точно синхронно с 3D-поворотом. У перемешанного кубика цвета смешаны; у собранного образуются 6 плотных одноцветных кластеров.

## N×N (2×2 – 15×15)

Меню «Головоломка» вверху предлагает 2×2 … 15×15 (также `?n=7`). Все виды (раскраска развёртки, формула, сетка камеры N×N, 3D на three.js, граф из трёх групп по n концентрических окружностей с масштабированием / сдвигом, плеер) создаются для каждого размера.

| Размер | Решатель | Метрика | Измерено (случайные скрамблы, все проверены как собранные) |
| --- | --- | --- | --- |
| 2×2 | Собственный оптимальный решатель (полная таблица расстояний, 3 674 160 состояний, BFS) | HTM | 100 решений: в среднем 8,87, макс. 10; таблица ≈ 0,3 с, решение < 1 мс |
| 3×3 | BFS ≤ 8 оптимально + двухфазный Коцемба с сокращением | HTM | обычно 19–21 ход |

| 5×5 – 15×15 | gullicube (T. Rokicki, MPL-2.0), скомпилированный в многопоточный WebAssembly; режим качества / быстрый | SSTM | см. таблицу ниже |

Устройства с малым объёмом памяти (`navigator.deviceMemory` < 4 ГБ) и телефоны / планшеты по умолчанию используют быстрый режим для n ≥ 5; меню решателя в любой момент переключает качество / скорость. Многопоточному WASM нужна межсайтовая изоляция: `deploy/_headers` задаёт COOP / COEP / CORP.

**Аналитика** (`js/analytics.js`, работает только на cube-solver.org): Cloudflare Web Analytics не использует cookie и загружается для всех; GA4 подключает gtag.js только после того, как посетитель нажмёт «Принять» (Consent Mode v2, разрешено только `analytics_storage`). Баннер показывается только в регионе согласия: `deploy/worker.js` ставит `<html data-consent="1">` для ЕС/ЕЭЗ, Великобритании, Швейцарии и неизвестных стран (`request.cf.country` нет, `XX`, `T1`) и `data-consent="0"` в остальных, где GA4 загружается без баннера (рекламные сигналы по-прежнему запрещены), а ссылка в подвале по-прежнему предлагает «Отклонить», что отключает GA и удаляет его cookie. ETag получает суффикс `-c1`/`-c0`, чтобы два варианта никогда не ревалидировали друг друга. Оба отвечают с `Cross-Origin-Resource-Policy: cross-origin` + заголовками CORS, поэтому `require-corp` остаётся и межсайтовая изоляция не нарушается. Смены маршрута SPA (`history.replaceState`) автоматически учитываются режимом SPA у CF и расширенной статистикой GA4 («смены страниц по событиям истории браузера»); не отправляйте `page_view` вручную (будет двойной счёт). Тесты: `npm run test:analytics` (локально, маяки перехватываются) / `npm run test:analytics:live`. Идентификаторов аналитики нет в репозитории: `tools/build-dist.js` читает `CF_BEACON_TOKEN` и `GA_MEASUREMENT_ID` из окружения (или из игнорируемого git файла `.env`) и записывает их только в `dist/js/analytics.js`; без них нет ни аналитики, ни баннера согласия, ни отслеживания. Всё укладывается в бесплатную квоту статических ресурсов Cloudflare Workers (статические файлы не тарифицируются как запросы к Worker; Worker запускается только для маршрутов страниц).

**Решатель 4×4 методом редукции** (`puzzles/nxn/cube4.worker.js`, собственный код; идея фаз следует открытым методам в духе Tsai / TPR, код не копировался):
1. P1 (36 ходов): центры цветов R/L на R/L, точная таблица расстояний C(24,8).
2. P2 (внешние слои + Rw/Lw + Uw2/Dw2/Fw2/Bw2): центры U/D на U/D, центры оси R/L в одну из 12 решаемых раскладок, все крылья «ориентированы» (24 позиции крыльев делятся на два класса под группой P3), чётная перестановка крыльев (устраняет OLL-паритет).
3. P3a (U D F B, R2 L2, широкие полуповороты): центры в подмножество, решаемое в P3b, 8 крыльев среза E обратно в срез E, P3b решаем.
4. P3b (U D, F2 B2 R2 L2, широкие полуповороты): центры собраны, 12 рёбер спарены, PLL-паритет устранён.
5. Эквивалентный 3×3 передаётся двухфазному Коцембе (cubejs).
Каждая фаза использует IDA*; в пределах бюджета времени пробуются несколько кандидатов из предыдущих фаз и сохраняется самый короткий; соседние ходы по одной оси объединяются.

Тесты: `node tests/nxn.test.js [выборки 4×4]` (модели 2–15 + 2×2 + 4×4), `node tests/gullicube.test.js 5,7,10,15 both`, на живом сайте `node tests/live-nxn.js <URL>`.

### Предвычисленные таблицы (решатели 4×4 и 3×3)

`npm run build:tables` записывает `puzzles/nxn/cube4-tables.bin.gz` (1,61 МБ, 7 таблиц расстояний) и `puzzles/cube3/cubejs-prune.bin.gz` (0,89 МБ, таблицы отсечения cubejs). Формат: `CLT1` + длина заголовка + JSON-каталог (имя / тип / длина / контрольная сумма FNV-1a) + сырые байты, сжатые gzip (`js/core/table-pack.js`). Worker загружает таблицы, пока строит таблицы ходов; браузер распаковывает их через `DecompressionStream`, проверяет каждую таблицу и возвращается к вычислению на месте, если загрузка не удалась, контрольная сумма не совпала или браузер этого не поддерживает. После изменения структуры таблиц решателя снова выполните `npm run build:tables` (`tests/tables.test.js` сравнивает таблицы с живым вычислением).

## Свободная игра (все головоломки)

Переключатель «Решение / Свободная игра» над сценой (или `?mode=play`).

| Действие | Описание |
|---|---|
| Перетащить наклейку (мышь / касание) | Поворачивает слой этой наклейки. Кубы: из двух осей грани выбирается та, проекция которой лучше совпадает с направлением перетаскивания; ось = нормаль грани × направление перетаскивания; на больших кубах поворачивается захваченный слой (внутренние слои 2R, 3R…, средний слой нечётных размеров M / E / S). Остальные головоломки используют `dragMoves` (ниже). При касании у холста `touch-action: none`, поэтому страница не прокручивается |
| Перетаскивание по пустому месту | Вращает вид (двойной клик — сброс) |
| Клавиатура | `U D L R F B` (Shift = против часовой); числовой префикс выбирает слой (`2` `R` → 2R); префикс `w` для широких ходов (`3` `w` `R` → 3Rw); `M E S` на нечётных размерах; перехваты `x y z` (2×2 и 4×4+); Ctrl+Z / Backspace — отмена, Ctrl+Y / Ctrl+Shift+Z — повтор; Esc сбрасывает префикс. Нотация следует текущему хвату (верхний слой на экране — всегда U) |
| Поле формулы | Любая формула (3Rw, 2R, M/E/S…), Enter выполняет её с пошаговой анимацией |
| Перемешать | 2×2 / 3×3: равномерно случайное состояние (`CubeLab.play.randomState`); 4×4+: случайные ходы; Пирамидка / Скьюб: равномерно случайное состояние; Мегаминкс: скрамбл WCA (Pochmann) |
| Таймер | Запускается первым ходом (не перехватом) после перемешивания, останавливается при сборке; по желанию 15-секундный осмотр WCA (+2 после 15 с, DNF после 17 с) |
| Число ходов | STM до 3×3, BTM для 4×4+ (перехваты не считаются); Пирамидка / Скьюб — VTM; Мегаминкс — HTM |
| Отменить / повторить / сбросить / решить из текущего состояния | «Решить» возвращает в режим решения и решает текущее состояние с обычным воспроизведением (эта попытка не засчитывается) |

- Лучшее время для каждой головоломки хранится в `localStorage` (`cubelab.best.<головоломка>`). При сборке — лёгкая подсветка + звук сборки (по переключателю эффектов) + круг показа (по переключателю автоповорота).
- Реализация: `js/core/play-core.js` (чистая логика, тестируемая в Node), `Player.pushMove / popMove` (очередь анимации, ускоряется при отставании и никогда не теряет ходы), `View3D.pick / dragTurn / setPlayMode` и управление режимами в `app.js`. Граф обновляется пошагово вместе с 3D.

## Пирамидка и Скьюб

Обе — полноценные плагины (`puzzles/twisty/`): модель, проверка, 3D, редактор развёртки, вид графа, строго оптимальный решатель, свободная игра, 12 языков.

- **Модель** (`twisty-model.js`, общая для страницы / worker / Node): наклейки строятся по геометрии (Пирамидка: 9 треугольников на грань; Скьюб: 1 квадрат + 4 угловых треугольника на грань); перестановка каждого хода = повернуть центроиды и нормали наклеек слоя на 120° вокруг оси и сопоставить наклейки. Нотация WCA: Пирамидка `U L R B` (два слоя) + `u l r b` (вершинки); Скьюб `R U L B` (R = угол низ-право-зад, U = верх-лево-зад, L = низ-лево-перед, B = низ-лево-зад; угол верх-право-перед неподвижен).
- **Оптимальный решатель** (`twisty.worker.js?p=…`): состояние цветов → детали + ориентации, разбитые по классам деталей на независимые компоненты; сначала BFS находит достижимое множество и таблицы ходов каждой компоненты, затем полный BFS по пространству произведения (таблица расстояний `Uint8Array`); решение спускается по таблице, поэтому его длина — ровно минимальное расстояние (VTM: каждый поворот на 120° считается за 1). Вершинки Пирамидки коммутируют со всем и доводятся в конце 0 / 1 ходом каждая (по-прежнему оптимально).

| | Состояния (ядро) | Компоненты | Измеренное число Бога | Таблица | Построение (Node / браузер с запуском worker) | Решение |
|---|---|---|---|---|---|---|
| Пирамидка | 933 120 (× 81 вершинка = 75 582 720) | рёбра 11 520 × осевые центры 81 | 11 (15 с вершинками) | 0,93 МБ | ≈ 60 мс / ≈ 250 мс | ≈ 0,03 мс |
| Скьюб | 3 149 280 | центры 360 × углы 8 748 | 11 (90 антиподов) | 3,15 МБ | ≈ 180 мс / ≈ 400 мс | ≈ 0,01 мс |

  Таблицы строятся в браузере (быстрее, чем загружать сжатую таблицу), так что дополнительный ресурс не нужен. `tests/twisty.test.js` проверяет: каждый ход в кубе = тождество, сокращается со своим обратным, перемещает целые детали; произведение компонент = число, достижимое BFS (компоненты независимы); число состояний по слоям; таблица — согласованное расслоение BFS; случайные состояния решаются с длиной = расстоянию по таблице; валидатор отклоняет перевёрнутые рёбра / закрученные углы / две переставленные детали / невозможные сочетания цветов / неверный хват.
- **3D**: каждая деталь — сплошной выпуклый многогранник (форма ∩ полупространства плоскостей разреза: по две у каждой вершины у Пирамидки, 4 плоскости через центр у Скьюба); поворот вращает весь слой, поверхности разреза скользят в своей плоскости и никогда не пересекаются; наклейки — утопленные скруглённые треугольники / квадраты.
- **Вид графа**: орбиты наклеек при каждом повороте на 120° — 3-циклы, рисуемые как окружность через 3 узла. Узлы Пирамидки = центры наклеек на развёртке (вершины U / L / R — центры групп концентрических окружностей, окружности слоя B охватывают всю развёртку); Скьюб использует азимутальную эквидистантную проекцию из угла DBL (слой B — концентрические окружности, R / U / L — три лепестка).
- **Редактор развёртки**: SVG-многоугольники (клик / перетаскивание для раскраски, Enter раскрашивает с клавиатуры, ошибки обведены красным). Пирамидка: передняя грань в центре, левая / правая грани по бокам, нижняя под ней; Скьюб: тот же крест, что и у куба.
- **Свободная игра**: при перетаскивании наклейки из ходов-кандидатов выбирается тот, где мгновенная скорость этой наклейки лучше всего совпадает с перетаскиванием (на одной оси — с меньшим числом деталей, поэтому перетаскивание вершинки поворачивает только вершинку); клавиши `U L R B` / `R U L B` (Shift = против часовой), на Пирамидке `T`, затем буква = вершинка; перемешивание = равномерно случайное состояние; таймер / лучшие результаты как у кубов.
- **Распознавание камерой / по фото**: пока не поддерживается (треугольным / ромбовидным наклейкам нужны новые сетки выборки и раскраска с ограничениями по деталям); у этих головоломок вкладка сканирования скрыта и предлагается раскраска.

## Мегаминкс

Полноценный плагин в `puzzles/megaminx/` (собственный код, MIT): `megaminx-model.js` (геометрия, ходы, проверка; общий для страницы / worker / Node), `megaminx.js` (плагин: 3D, развёртка, граф, нотация, свободная игра), `megaminx-solver.js` (многофазный решатель), `megaminx.worker.js` и `megaminx-ll.json` (таблица последнего слоя, создаётся офлайн скриптом `tools/megaminx-ll-gen.js`).

- **Модель**: 12 граней × 11 наклеек = 132 наклейки, 62 детали (12 центров, 30 рёбер, 20 углов). Ходы граней `U F R L BL BR D DR DL B FL FR` с `X X' X2 X2'` (72° / 144°, по часовой, если смотреть на эту грань); ходы WCA Pochmann `R++ R-- D++ D--` (всё, кроме слоя L / U, поворачивается на 144°). Перестановка каждого хода получается поворотом центроидов и нормалей наклеек. Проверка: число цветов, невозможные или повторяющиеся детали, закрученные углы, перевёрнутые рёбра, чётность перестановки и расположение центров (`v.megaCenters`).
- **Решатель** (многофазный, не оптимальный, HTM в стиле WCA: любой поворот грани на 72° или 144° считается за 1):
  1. После проверки состояние поворачивается / переименовывается так, чтобы центры соответствовали стандартной схеме, и переводится в коды деталей (угол: место × 3 ориентации, ребро: место × 2).
  2. **F2L, грань за гранью**: D, пять граней кольца вокруг D, затем четыре из пяти верхних граней. Когда все детали грани расставлены, эту грань больше не поворачивают — набор ходов S сужается, и нетронутые детали остаются собранными. Новые детали каждого шага делятся на небольшие группы (≤ 3 детали: угол и соседние с ним рёбра); каждая группа решается IDA*, эвристика которого — максимум из небольших таблиц расстояний для групп деталей (BFS при текущем S, строятся при первом использовании и кэшируются). Перед последним двухгранным шагом добавляется таблица ориентации рёбер (как EO `<R,U>` для 3×3), чтобы этот шаг завершался двумя образующими. Бюджет узлов с повторными попытками (со следующим решением предыдущей группы) держит редкие медленные случаи короткими.
  3. **Последний слой в два «взгляда»** по таблице: взгляд 1 = перестановка рёбер + ориентация рёбер + ориентация углов (60 · 16 · 81 = 77 760 состояний), взгляд 2 = перестановка углов × перестановка рёбер (3 600 состояний). Генератор обходит трёхгранные подгруппы `<U,X,Y>` методом встречи посередине (≤ 7 ходов с каждой стороны) в поиске последовательностей, сохраняющих все детали вне U, оставляет кратчайшую для каждого действия вместе с её 5 поворотами по U (39 059 макросов), затем запускает Дейкстру со стоимостью HTM.
  4. Соседние ходы одной грани объединяются (единицы по 72° по модулю 5).
- **Измерено** (Node, `tests/megaminx.test.js` / бенчмарк): 1000 случайных состояний, все решены: в среднем 120,1 HTM (F2L 95,4 + последний слой 26,4), макс. 135, мин. 97; время решения в среднем 34 мс, макс. 1,6 с. 500 скрамблов Pochmann: в среднем 119,7, макс. 135, в среднем 29 мс, макс. 0,9 с. В браузере решение обычно занимает 2–20 мс плюс накладные расходы worker; запуск worker + загрузка таблицы ≈ 170–200 мс. Эти числа записаны в `seo/site.config.json` и показываются на SEO-страницах.
- **3D**: `view3d.geometry: 'poly'` с додекаэдром в качестве `solid` и 12 плоскостями разреза в качестве `cuts`; детали — выпуклые многогранники.
- **Вид графа**: стереографическая проекция положений наклеек из центра грани D (этот один узел скрыт). Каждый поворот грани на 72° перемещает её наклейки 5-циклами, и 5 точек каждого цикла лежат в проекции на одной окружности (стереографическая проекция переводит окружности в окружности); поэтому каждая орбита рисуется как описанная окружность своего 5-цикла: 39 окружностей, 131 видимый узел. Белая грань U — в середине, верхние грани вокруг неё, нижние — большие внешние лепестки; масштабирование показывает плотный центр.
- **Редактор развёртки**: два «цветка» из 6 пятиугольников рядом (U с 5 соседями, D с 5 соседями), SVG-многоугольники, как у других форм.
- **Свободная игра**: перетаскивание (общий `dragMoves`), клавиши `U F R L B D` плюс `I`=BL, `O`=BR, `J`=FL, `K`=FR, `N`=DL, `M`=DR (Shift = против часовой); подсчёт в HTM; перемешивание = скрамбл WCA Pochmann из 77 ходов (7 строк `R±± D±±` × 5 + `U`/`U'`); «решить из текущего состояния» работает как у других головоломок.
- **Сканирование камерой**: скрыто (`cameraPlan: null`).
- **Названия**: 五魔方 (zh), メガミンクス (ja), Мегаминкс (ru), ميغامينكس (ar), в остальных языках Megaminx; в меню сразу после Скьюба.

## Точки расширения (архитектура)

Основные модули (ввод, вид графа, 3D, плеер, сканирование, клиент решателя) работают **только** через объект Puzzle, зарегистрированный `CubeLab.registerPuzzle(def)`, и не содержат логики, специфичной для 3×3. Новая головоломка размещается в `puzzles/<id>/` и реализует интерфейс ниже.

### Интерфейс Puzzle

```js
CubeLab.registerPuzzle({
  id: 'cube3', name: '3×3 Cube',
  colors: { W: { name: 'White', hex: '#f5f5f5' }, ... },  // color set
  blankColor: '#cfcfc6',                                 // display color of unpainted stickers

  // stickers: a state is an array of color keys, one per sticker
  stickers: [{ id: 'U1', face: 'U', pos: [x,y,z], normal: [nx,ny,nz], locked?: true }, ...],
  faces:    [{ id: 'U', name: 'Up', center: 4, normal: [0,1,0], stickers: [0..8] }, ...],
  pieces:   [{ pos: [x,y,z], stickers: [i, j, k] }, ...],  // pieces rendered in 3D

  // a move is a sticker permutation: perm[i] is where sticker i goes
  moves: { "R": { perm, axis: [1,0,0], angle: -Math.PI/2, base: 'R', face: 'R', inverse: "R'", layer: pos => bool }, ... },
  trackMoves: ['U','R','F','D','L','B','M','E','S'],     // base moves used to build graph tracks
  holds: [{ id, name, short, orientation: [ex,ey,ez], toView: {internal: shown}, fromView }],  // optional grips

  solvedState(), randomScramble() -> [tok], validate(state) -> { ok, errors: [...] },
  describeMove(tok) -> 'Right face clockwise 90°…',
  netLayout: { cols, rows, cells: [{ sticker, col, row }] },  // net editor
  graphLayout(opts) -> { nodes: [[x,y]] (one per sticker), clusters: [[stickerIds]], nodeRadius, circles? },
  cameraPlan: [{ face, title, instruction, grid: 3, cells: [...], center }],  // null hides the scan tab
  notation: [[symbol, description], ...],
  view3d: { ... },
  solvers: [ /* see below */ ]
});
```

При регистрации ядро дополняет стандартные `parse / format / apply / inverse / isSolved`, детали, поворачиваемые каждым ходом (определяются по `layer`), **дорожки графа** (`P.tracks`) и пути наклеек для каждого хода (`moves[tok].paths`).

Необязательные поля, используемые другими формами: `trackMode: 'cycles'` (дорожки = циклы перестановок базовых ходов), `netLayout.polys` (развёртка из SVG-многоугольников), `view3d.geometry: 'poly'` + `solid` / `cuts` / `core` (детали — выпуклые многогранники), `dragMoves` (общее перетаскивание), `playKeys` / `playMetric` / `metricTitle`, `hints` (ключи i18n для подсказок), `randomState(rnd)` (равномерно случайное состояние), `randomScramble()`, `nameKey`; `cameraPlan: null` скрывает вкладку сканирования, а без `holds` меню хвата скрыто.

### Дорожки графа и движение (`CubeLab.buildTracks` + `GraphView`)

Для каждого базового хода: берутся перемещаемые наклейки, группируются по «нормаль наклейки · ось» (для 3×3: «8 на грани» и «12 по бокам»), каждая группа сортируется по углу вокруг оси в замкнутое кольцо; поворот на θ сдвигает наклейки по кольцу на `θ/2π × n` позиций, что сверяется с `perm`.

`graphLayout()` плагина задаёт 2D-положения узлов и, по желанию, `circles: [{id, cx, cy, r}]`:
- если все узлы боковой дорожки лежат на окружности, они движутся **по этой окружности** (в одном направлении для всей дорожки; направление с кратчайшим суммарным путём при базовом ходе, обратное для обратного хода) с цветными следами;
- узлы дорожки «грани» интерполируются в полярных координатах вокруг центрального узла грани (кластер вращается как целое);
- без окружностей используется замкнутый сплайн через узлы, так что другие головоломки можно визуализировать без ручной раскладки.

**Раскладка 3×3** (конфигурация `GL` в `puzzles/cube3/cube3.js`): три группы концентрических окружностей — оси y (U/E/D), z (F/S/B) и x (R/M/L), с центрами в вершинах равностороннего треугольника (верх, низ слева, низ справа), радиусы 1,3922 / 1,7696 / 2,1469 (радиус описанной окружности треугольника = 1). Эти значения получены подгонкой методом наименьших квадратов по **всем 54 узлам** на эталонном кадре высокого разрешения (среднеквадратичный остаток 0,2 пкс); радиус узла 0,184, толщина линии 0,048, ширина дорожки 0,063 и ширина подсветки 0,076 взяты из пиксельных измерений того же кадра. При отрисовке с пиксельным соответствием эталонного кадра и наложении с 50 % прозрачностью окружности и узлы совпадают почти идеально (`tests/graph-pixel.html`). Наклейки грани X лежат на пересечениях групп окружностей двух осей, кроме нормали X; две области пересечения вмещают пару противоположных граней. Направление слой→радиус (`sign`) и область пересечения каждой грани (`upper`) проверены полным перебором (64 комбинации): каждый из шести поворотов граней — циклический сдвиг 12 узлов по одной окружности. Ходы срезов M/E/S — настоящие ходы (генерируются по геометрии в `moves`; тот же генератор точно воспроизводит 6 перестановок граней, что проверено модульным тестом) и идут по средней окружности своей группы. Решатель выдаёт только ходы граней.

**Прокладка дуг (сверено покадрово с эталонным видео)**: 12 узлов каждой окружности принадлежат 4 секторам граней с интервалами примерно 60°/60°/60°/180°. С правилом «кратчайший суммарный путь» поворот на 90° перемещает 9 наклеек по дугам ≈ 60°, а **3 наклейки одного сектора — через пустую дугу в 180°** (например, верхняя дуга внешней окружности, большая левая дуга группы внизу слева). Эталонное видео делает ровно то же самое (`screenshots/compare-motion.png`, вторая строка). Положение секторов зафиксировано условием «собранная раскладка = эталон f14», поэтому никакое другое назначение не делает все дуги короткими.

**Время и сглаживание (измерены по энергии движения эталонного видео при 60 кадр/с)**:
- сглаживание отдельного шага `easeInOutQuad` (подогнано к средней кривой скорости 15 поворотов, RMS 0,076; sine 0,155, cubic 0,193);
- непрерывное воспроизведение следует огибающей «медленный старт — ускорение — медленный конец»: первый шаг ≈ 0,85 с, середина 0,48 с, последний ≈ 1,0 с, между шагами всего ≈ 0,07 с (`CubeLab.tempo(i, n)`, `Player.baseMs = 480`, `gapMs = 67`; одиночное «вперёд» всегда 0,55 с);
- подсветка активной окружности появляется за первые 8 % поворота и гаснет за последние 16 %; цветные следы тянутся назад от узла (фаза хвоста `ease(1.6t − 0.6)`) и исчезают в конце;
- после сборки ≈ 1,2 с паузы, затем 2,0-секундный круг показа.

### Хваты (точка зрения нотации)

Внутреннее состояние, решатели и ввод формул всегда используют хват WCA (белый U, зелёный F). Плагин может задать `holds`: каждый хват даёт общую 3D-ориентацию и таблицу переименования нотации. Хват 3×3 по умолчанию «жёлтый сверху, зелёный спереди» = стандартный хват, повёрнутый на 180° вокруг оси перед–зад (z2): `U↔D`, `R↔L`, `F/B` без изменений, `M→M′`, `E→E′`, `S` без изменений (модульные тесты проверяют каждый: ось × угол внутреннего хода, повёрнутые ориентацией, равны оси × углу отображаемого хода). Текст решения, текущий шаг плеера, список шагов и описания используют нотацию текущего хвата, поэтому верхний слой на экране называется U.

### 3D-стиль и вид

- `view3d.style: 'plastic'`: светло-серый корпус + белые панели (тонкие светло-серые швы) + скруглённые наклейки сплошного цвета (без освещения, те же цвета, что в графе) + мягкое затенение корпуса; без него — классический плоский стиль с чёрным корпусом.
- `stickerCorners: [верх-лево, верх-право, низ-право, низ-лево]`: радиусы углов наклеек (возможны асимметричные формы листа); `stickerColors` переопределяет цвета 3D-наклеек.
- `orientation` (углы Эйлера, переопределяются текущим хватом) + `camera: { fov, dir }`: вид 3×3 по умолчанию совпадает с эталонным видео — жёлтый (D) сверху, зелёный (F) слева, оранжевый (L) справа, — то есть с тремя кластерами центрального треугольника графа. Перспектива FOV 24°, угол возвышения около 25°, подобрано попиксельным сравнением с эталонными кадрами.
- `frame: { width, height, dx, dy }`: кадрирование (размер и смещение головоломки / графа в своих половинах), совпадает с эталонным видео с точностью до 0,5 %.
- `autoRotate`: при воспроизведении головоломка слегка покачивается; когда воспроизведение доходит до конца в собранном состоянии, она стоит `showcaseDelay` (1,2 с), делает один оборот за `showcaseMs` (2,0 с) и возвращается к исходному виду (как в конце эталонного видео). Переключатель «автоповорот» в плеере отключает это; вращение перетаскиванием и сброс двойным кликом работают всегда.

### Звук (`js/core/audio.js`, `CubeLab.SoundEngine`)

Всё синтезируется на лету через Web Audio API; нет ни аудиофайлов, ни сторонних ресурсов.
- **Политика автовоспроизведения**: при загрузке страницы `AudioContext` не создаётся; он создаётся и запускается через `resume()` при первом `pointerdown / keydown / touchstart`. По умолчанию эффекты включены, музыка выключена; «эффекты / музыка / громкость» хранятся в `localStorage` (`cubelab.sfx / cubelab.music / cubelab.vol`). Если музыка была включена до перезагрузки, она ждёт следующего действия пользователя. Без Web Audio каждый вызов ничего не делает, а элементы управления отключены.
- **Звук поворота v3** (хук `Player.onMove(phase, tok, durMs)`): переделан по анализу трёх реальных записей 3×3 (см. `user-sounds/ANALYSIS.md`, `screenshots/sound-compare.png`). Реальный поворот = серия сгруппированных пластиковых «зёрен» длиной 120–200 мс (≈ одно каждые 5 мс), возбуждающих короткие моды корпуса: главный пик 0,86–1,1 кГц («полый / деревянный») + 500 Гц, 1,55, 2,8, 4,1 кГц, звон всего 3–6 мс, почти нет гула ниже 300 Гц; энергия нарастает до самого громкого щелчка при фиксации слоя, затем 70–100 мс затухающего дребезга. Синтез: сгенерированные в JS события зёрен → 10 резонаторов второго порядка (каждое зерно случайно возбуждает разные моды) + тонкий слой микрозёрен + очень лёгкое трение + широкополосная прямая атака; щелчок фиксации совпадает с концом анимации, медленное воспроизведение сосредотачивает звук в конце, повороты на 180° получают щелчок на T/2, срезы мягче и темнее; каждый звук рассчитывается за 1,7–3,3 мс. Сравнение с реальными записями (материалы SpaceJoe / Pixabay, тот же анализ): центроид 2141 Гц против 2135 / 2077 Гц, пик-фактор 20,7 против 21,1 / 17,6 дБ, плоскость спектра 0,24 против 0,25 / 0,32, 18,5 против 17,8 / 12,0 зерна на 100 мс, отличие формы по третьоктавным полосам ≈ 2 дБ. Аудиофайлы не публикуются (записи использовались только для анализа; лицензии в `vendor/sounds/LICENSE.txt`). Защита при быстром воспроизведении: не менее 50 мс между звуками поворота; более короткие повороты тише и содержат меньше зёрен; перетаскивание шкалы сразу останавливает незавершённые звуки поворота.
- **Сборка**: восходящее мажорное арпеджио + аккорд (когда воспроизведение доходит до последнего шага в собранном состоянии); мягкое восходящее мерцание в начале **круга показа** (`View3D.onShowcaseStart`).
- **Интерфейс**: щелчки раскраски (высота тона зависит от цвета, ограничиваются при раскраске перетаскиванием), сигналы успешной съёмки / загрузки (три ноты, когда все шесть граней готовы).
- **Фоновая музыка**: 72 BPM, четырёхтактовый цикл Cmaj9 – Am9 – Fmaj9 – G6sus; расстроенные пилообразные волны с фильтром нижних частот в качестве пэда + пентатонические арпеджио (детерминированно псевдослучайные), задержка с обратной связью для пространства; планирование наперёд (каждые 150 мс в очередь ставится 0,6 с), бесшовный цикл, плавное появление и затухание, очень тихо.
- Уровни (громкость 0,8, измерено офлайн): одиночный поворот при 1× достигает пиков около 0,31–0,36, при реальной скорости рук (130 мс) около 0,22, арпеджио сборки около 0,23, фоновая музыка — пики около −22 dBFS. Демо (только локально): `screenshots/sound-demo-turns.wav`, `sound-demo-turns-v3.wav`, `sound-demo-sfx.wav`, `sound-demo-music.wav`.

### Языки (`js/i18n/`, `CubeLab.i18n`)

- **Языки и порядок**: English, 简体中文, 繁體中文, Español, العربية, Português, Bahasa Indonesia, Bahasa Melayu, Français, 日本語, Русский, Deutsch (все равноправны в меню, без групп).
- **Строки**: по одному файлу на язык, `js/i18n/<code>.js`, вызывающему `CubeLab.i18n.register(code, {key: text})`; `en.js` — главная таблица, отсутствующие ключи берутся из английского и записываются в `CubeLab.i18n.missing`. HTML использует `data-i18n` / `data-i18n-title` / `data-i18n-aria` / `data-i18n-placeholder`; динамический текст использует `I.bind(el, key, params)` и перерисовывается при смене языка.
- **Форматирование**: подмножество ICU — `{name}`, `{n, plural, =0 {…} one {# …} few {…} many {…} other {…}}` (`Intl.PluralRules`), `{ms, unit, millisecond}`, `{x, number}` (`Intl.NumberFormat`). Во французском автоматически ставятся неразрывные пробелы перед `: ; ! ? « »`; в испанском используются ¡ ¿. Нотация ходов во всех языках сохраняет стандартные буквы (U D L R F B M E S, ′ 2).
- **Порядок определения**: `?lang=xx` → `localStorage['cubelab.lang']` → `navigator.languages` (zh-TW/HK/MO/Hant → традиционный, прочие zh → упрощённый) → English. Задаёт `<html lang dir>`, заголовок и meta description.
- **RTL**: арабский зеркально отражает всю страницу (логические свойства CSS); 3D-холст, граф, шкала / кнопки плеера, полоса шагов, нотация, ввод формулы и числа остаются LTR (`dir="ltr"`).
- **Типографика**: для CJK / арабского — свои наборы шрифтов, увеличенный межстрочный интервал и без разрядки; для немецкого / русского включён `hyphens:auto`, и кнопки могут переноситься, а не выходить за край.
- **Добавить язык**: добавьте запись в `LANGS` в `i18n.js`, создайте `js/i18n/<code>.js` и подключите его в `index.html`, затем выполните `node tests/i18n.unit.test.js`.

### Адаптеры решателей

```js
solvers: [
  { id: 'kociemba', name: '…', available: true,
    workerUrl: 'puzzles/cube3/kociemba.worker.js',
    encode: state => payload },          // runs on the main thread; throws a localized error for invalid states
  { id: 'optimal-ida', name: 'IDA* optimal (planned)', available: false }
]
```

Протокол worker:

```
→ { id, cmd: 'init' }                      ← { id, ok: true, ms }
→ { id, cmd: 'solve', payload }            ← { id, ok: true, moves: ['R', "U'", ...], optimal?: bool, label?, note?, ms }
                                           ← { id, ok: false, error }
```

У головоломки может быть несколько решателей; меню перечисляет их автоматически, а `available: false` показывается как «запланировано». Для настоящего оптимального решателя (например, IDA* Корфа с базами шаблонов для углов / рёбер) нужен лишь новый worker, зарегистрированный в `solvers`. Worker может вернуть `optimal: false` с ключом i18n `label` / `note` (так делает Мегаминкс), и интерфейс покажет его рядом с числом ходов.

### Другие виды

Плеер (`CubeLab.Player`) управляет любым числом видов; вид реализует лишь `setState(state)` и `animate(tok, e, fromState, t)` (e = сглаженный прогресс 0–1, t = исходная временная фаза) и, по желанию, `highlight(tok, state)`. Новой визуализации (например, графу Кэли или диаграмме циклов) нужны только эти методы.

## Известные ограничения

- Пирамидка / Скьюб / Мегаминкс: распознавания камерой / по фото пока нет. При раскраске держите головоломку так, как указано в подсказках (Пирамидка: осевая деталь без жёлтого сверху, деталь без зелёного сзади; Скьюб: бело-зелёно-красный угол верх-право-перед; Мегаминкс: центры должны образовывать стандартную цветовую схему), иначе появится ошибка хвата / центров.
- Решения Мегаминкса **не оптимальны** (в среднем ≈ 120 HTM, до ≈ 135); изредка сложное состояние занимает до ≈ 1,6 с; таблица последнего слоя размером 1,8 МБ (`megaminx-ll.json`, при передаче сжимается) загружается один раз при запуске решателя Мегаминкса.
- Камере нужен HTTPS или localhost; распознавание зависит от освещения — при сильных бликах или жёлтом свете исправьте результат на развёртке (цвета центров используются для калибровки и выдерживают некоторый оттенок).
- Сканирование предполагает стандартную цветовую схему (белый напротив жёлтого, зелёный напротив синего, красный напротив оранжевого) и управляемый хват; центры в редакторе фиксированы.
- Решатель 3×3 выдаёт только ходы граней (HTM); решения в эталонном видео содержат ходы срезов, поэтому последовательность шагов для того же состояния отличается от видео.
- Двухфазный алгоритм даёт почти оптимальные решения (обычно 19–21 ход); доказуемо оптимальное решение получают только состояния с ≤ 8 ходами. Настоящий оптимальный решатель уровня «числа Бога» остаётся возможным расширением.
